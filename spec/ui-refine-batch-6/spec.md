# Feature Specification: 聊天核心缺陷修复与交互改造（第七批）

**Created**: 2026-10-31
**Status**: Approved
**Input**: User description: "①有时候聊天记录会出两次一模一样的 ②有时候流式消息到一半就没了，必须重启 app 才可以再次看到；希望重启 app 之后如果还在流式输出就继续流式输出，看看有什么方案 ③正在流式输出时文字框应该一直光晕旋转，现在一重启就不旋转了 ④新建会话页面中间一堆小图标换成『开启一段新对话吧，什么都可以说。』 ⑤发送完对话后输入框和软键盘一起收起（可参考：输入控制器 stopEditing、发送按钮空输入置灰、聚焦边框 1dp→2dp） ⑥发送后聊天列表自动滚动到底部，刚发的消息直接可见 ⑦接收消息显示工具调用时会一直跳到最近的上一条消息，直到有回答才跳到回答，改成工具调用也直接跳到最底部"

## Overview

修复聊天流式链路的四类核心缺陷并改造发送交互：新会话竞态导致的消息重复/流式气泡脱钩消失；App 重启后活跃回合无法续流（含输入卡流光边框停转）；空态图标群与文案替换；发送后收键盘、空输入置灰、聚焦边框加粗、以及列表滚动索引错位（发送/工具调用时跳错位置）。全部为客户端（OctopLink HarmonyOS 端）改动，服务器零改动。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 历史加载与本地流式状态竞态修复：消息不重复、流式不消失 (Priority: P1)

用户在新会话发送第一条消息后，本地立即显示用户消息与流式回复占位；期间由会话切换触发的历史加载不得覆盖或复制本地进行中的消息。流式增量必须始终写入当前可见的气泡，回复完成后立即完整可见，无需重启 App。

**Why this priority**: 消息重复与流式中断消失是数据正确性缺陷，直接破坏聊天核心体验，属最高优先级。

**Independent Test**: 新会话连续发送 2-3 条消息（含流式进行中追加追问），检查每条用户消息只出现一次、流式文本持续增长直至完整显示。

**Acceptance Scenarios**:

1. **Given** 欢迎态（无活跃会话），**When** 用户输入并发送第一条消息，**Then** 用户消息与流式占位立即出现，流式文本持续可见增长，最终回复完整显示，全程用户消息只出现一次
2. **Given** 流式回复进行中，**When** 历史加载（由会话创建/切换触发的异步返回）晚于本地消息插入到达，**Then** 已插入的用户消息与流式气泡不被覆盖、不重复、不消失，流式增量继续写入同一气泡
3. **Given** 流式回复进行中，**When** 服务端 drain 追问后回发正式用户气泡（steer echo），**Then** 若本地已存在同文本的用户消息则不重复插入
4. **Given** 任意时刻，**When** 历史加载返回，**Then** 服务端结果与本地进行中消息合并后展示：已在服务端落库的消息以服务端为准，尚未落库的本地 fresh 用户消息与流式占位保留在列表尾部

---

### User Story 2 - App 重启后活跃回合续流（含输入卡流光恢复） (Priority: P1)

App 在服务端回合仍进行中时被杀掉重启：重新进入该会话后，客户端通过订阅应答感知回合仍在进行，重建流式气泡继续接收后续增量；回合结束时以服务端权威完整消息补齐（覆盖重启前漏掉的帧）。流式期间输入卡流光边框（"光晕旋转"）恢复流动。

**Why this priority**: 与 US1 同为流式链路正确性核心缺陷；重启续流是用户明确提出的方案探索需求（服务端已具备订阅应答 + 实时帧广播能力，纯客户端可达成）。

**Independent Test**: 模拟器上发送长回复请求，流式输出中途杀掉 App 重启，进入同一会话，观察流式气泡重建、增量继续、结束时文本完整。

**Acceptance Scenarios**:

1. **Given** 服务端回合仍在流式输出，**When** App 重启并进入该会话，**Then** 列表尾部出现流式助手气泡并随后续帧持续增长（状态提示如"恢复续流中/正在生成"）
2. **Given** 重启续流已建立，**When** 服务端回合结束（turn 结束帧到达），**Then** 客户端拉取服务端权威最终消息补齐气泡（补上重启前缺失的部分），标记完成，不误标"回复中断"
3. **Given** 重启后订阅应答表明回合已不活跃（active=false），**When** 历史已加载，**Then** 不创建流式气泡，正常展示落库消息
4. **Given** 重启续流期间，**When** 流式状态为真，**Then** 输入卡流光边框恢复流动旋转（此前重启后不再旋转）
5. **Given** 订阅应答（active=true）早于/晚于历史加载返回两种时序，**When** 各自发生，**Then** 均能正确重建或保留流式气泡，不出现空白气泡残留或气泡丢失

### User Story 3 - 滚动位置修复：发送、文本增量、工具调用一律滚到真底部 (Priority: P1)

用户发送消息、流式文本增长、工具调用 badge/详情出现时，列表滚动目标必须落在真实底部（最后一条消息），而不是因前置占位项（标题栏占位、加载更早条目、审批卡）导致的偏移错位项（表现为"跳到最近的上一条消息"）。

**Why this priority**: 滚动错位让用户在关键交互时刻看不到最新内容，与 US1/US2 同属核心体验缺陷。

**Independent Test**: 发送消息触发带工具调用的回复，观察每次工具调用 badge 出现与文本增量时列表始终显示最底部内容。

**Acceptance Scenarios**:

1. **Given** 会话含较多历史消息（可滚动），**When** 用户发送消息，**Then** 列表滚动使刚发送的用户消息与流式占位立即可见（位于视口底部）
2. **Given** 流式回复中发生工具调用，**When** 工具调用 badge/卡片/工具名提示出现，**Then** 列表滚动到最新内容底部，不再停留在倒数第二/三条消息
3. **Given** 存在"加载更早的消息"条目或审批卡等尾部/头部附加项，**When** 任一滚动触发时机到来，**Then** 滚动目标始终为列表真实底端，不受附加项数量影响
4. **Given** 打开已有历史的会话，**When** 历史加载完成，**Then** 初始定位同样落在真实底部（首屏直接显示最新消息）

### User Story 4 - 发送交互：发送后收键盘、空输入置灰、聚焦边框加粗 (Priority: P2)

用户点击发送后，输入框清空且软键盘一起收起；空闲状态下输入为空时发送按钮置灰不可用；输入框聚焦时输入卡边框由 1dp 加粗为 2dp，失焦恢复 1dp。

**Why this priority**: 高频交互体验打磨，降低误触与视觉反馈缺失，但非数据正确性问题。

**Independent Test**: 空态检查发送按钮置灰；输入文字后变亮可点；点击发送后键盘收起、输入清空、按钮回到置灰。

**Acceptance Scenarios**:

1. **Given** 空闲状态（非流式）且输入框为空，**When** 查看发送按钮，**Then** 按钮呈置灰禁用态，点击无发送动作
2. **Given** 输入框有内容，**When** 点击发送，**Then** 消息发出、输入框清空、软键盘收起、发送按钮回到置灰态
3. **Given** 输入框聚焦（键盘弹出），**When** 查看输入卡边框，**Then** 边框宽度为 2dp；失焦后恢复 1dp
4. **Given** 流式回复进行中，**When** 查看发送区，**Then** 停止/追问按钮行为保持现状不受影响（空输入显示停止按钮、有输入显示追问发送）

---

### User Story 5 - 新建会话空态文案替换 (Priority: P2)

新建会话（欢迎态）页面中间的图标/快捷提示元素群替换为居中文案"开启一段新对话吧，什么都可以说。"。

**Why this priority**: 空态视觉简化，明确独立，可与 P1 并行。

**Independent Test**: 点击新会话按钮回到欢迎态，检查中间区域显示指定文案且不再出现原小图标群。

**Acceptance Scenarios**:

1. **Given** 任意会话中，**When** 用户点击"新对话"回到欢迎态，**Then** 空态中间显示文案"开启一段新对话吧，什么都可以说。"，原快捷提示 chips 图标群不再显示
2. **Given** 欢迎态，**When** 文案展示，**Then** 布局居中、样式与现有空态视觉规范一致（字号/颜色/间距协调）

### Edge Cases

- 流式中断网：保留既有弱流恢复逻辑（自动重连、恢复续流提示、4 次失败标记中断），本批改动不得破坏
- 重启时回合恰好在订阅应答前后结束的竞态：回合结束帧晚到时按权威消息补齐；应答为不活跃时不建气泡
- 历史加载失败：保留现有错误重试态，不因合并逻辑引入新崩溃路径
- 追问（steer）与审批（HITL）流：发送交互改动不得影响追问发送与审批恢复按钮
- 输入仅为空白字符：视为空输入（发送按钮置灰、发送动作忽略）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在历史加载返回时与本地进行中消息（未落库的 fresh 用户消息、流式助手占位）合并展示，不覆盖、不丢失、不重复
- **FR-002**: 系统 MUST 在 steer echo 用户气泡插入前检查尾部是否已存在同文本用户消息，存在则不重复插入
- **FR-003**: 系统 MUST 在订阅应答表明回合活跃且本地无流式气泡时重建流式气泡并置流式状态为真，继续接收后续帧
- **FR-004**: 系统 MUST 在重启续流的回合结束时以服务端权威最终消息补齐流式气泡内容
- **FR-005**: 系统 MUST 在流式状态为真期间保持输入卡流光边框挂载流动，状态恢复时自动恢复流动
- **FR-006**: 系统 MUST 使所有滚动触发时机（发送、文本增量、工具调用、工具名提示、附件、初始定位）的滚动目标为列表真实底端
- **FR-007**: 系统 MUST 在空闲且输入为空（含纯空白）时将发送按钮置灰禁用；有内容时恢复可用
- **FR-008**: 系统 MUST 在发送成功后清空输入框并收起软键盘
- **FR-009**: 系统 MUST 在输入框聚焦时将输入卡边框宽度增至 2dp，失焦恢复 1dp
- **FR-010**: 系统 MUST 在新建会话空态中间展示文案"开启一段新对话吧，什么都可以说。"并移除原快捷提示图标群
- **FR-011**: 以上全部改动 MUST 仅限客户端，服务器端零改动

### Key Entities

- **流式助手气泡（ChatMessageModel streaming 占位）**: 本地创建的流式接收载体；竞态修复后必须始终保留在消息列表中直至回合结束
- **订阅应答（turn_status active）**: 服务端在订阅线程后返回的回合活跃标志；重启续流的判定依据
- **本地 fresh 用户消息**: 客户端先行插入、尚未在服务端落库的用户消息；历史合并时按角色+文本判重
- **输入卡流光边框（InputFlowBorder）**: 挂载条件为流式状态的输入卡边缘流光视效

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新会话发送与追问全流程中，任一用户消息在列表中出现次数为 1（0 重复）
- **SC-002**: 流式回复期间气泡文本单调增长不消失；正常网络下无需重启 App 即可看到完整回复
- **SC-003**: 服务端回合活跃时重启 App，进入会话后 3 秒内出现流式气泡并继续增长，结束时内容与服务端落库消息一致
- **SC-004**: 发送/工具调用/文本增量触发滚动后，视口底部内容为列表最后一项（含审批卡时为审批卡）
- **SC-005**: 发送后软键盘收起且输入清空；空输入时发送按钮不可用态可辨识
- **SC-006**: 新建会话空态文案与需求文字逐字一致

## Assumptions

- 服务端现有契约（订阅应答含回合活跃标志、活跃回合后续帧实时广播、回合结束消息落库）满足续流需求，无需服务端改动
- 普通线程重启后服务端不回放重启前的历史帧，缺失部分由回合结束时的权威消息拉取补齐（已验证服务端行为）
- 用户所述"文字框光晕"指输入卡流光边框（InputFlowBorder），其停转根因即重启后流式状态未恢复
- 用户所述"一堆小图标"指欢迎态快捷提示 chips 元素群（含纸飞机小图标），随空态文案替换一并移除
- 发送按钮置灰沿用现有按钮视觉语言（降低前景/背景对比），不引入新颜色资源
- 聚焦边框 2dp 仅改变宽度，边框颜色沿用现有 card_stroke
- 部署验证一律使用模拟器（127.0.0.1:5555）；真机部署仅用户明确要求时执行
